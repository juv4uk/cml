## 1. Головна теза / Core Thesis

### Українською
Справжня суверенність мови програмування досягається тоді, коли вона перестає бути «вертикально обрізаним» шаром, залежним від чужих непрозорих компіляторних стеків (LLVM, GCC, GNU binutils). 

Якщо компілятор та його проміжне представлення (`MachineInst`) виражаються через сам Лісп, **Лісп стає власним асемблером**. Це не означає захаращення математичного ядра `my-lisp` регістрами процесора. Це означає, що програма-асемблер, правила кодування інструкцій та бібліотеки повторюваних машинних шаблонів пишуться на чистому Ліспі як модульні структури даних (S-вирази) та макроси.

У такому розумінні `my-lisp` стає **повноцінною мовою програмування у найширшому сенсі слова**: єдиний концептуальний континуум поєднує чисті λ-обчислення, символьну логіку, макроси, типізовану компіляцію, машинний асемблер та безпосередню генерацію фізичних байтів під голе залізо (x86-64, FPGA, UEFI).

### English
True programming language sovereignty is achieved when a language ceases to be a "vertically amputated" layer dependent on opaque third-party toolchain monoliths (LLVM, GCC, GNU binutils).

When the compiler and its machine intermediate representation (`MachineInst`) are expressed in Lisp itself, **Lisp becomes its own native assembler**. This does not mean polluting the pure mathematical core of `my-lisp` with CPU registers. It means that the assembler program, the instruction encoding rules, and the libraries of reusable machine idioms are written in pure Lisp as modular data structures (S-expressions) and macros.

In this sense, `my-lisp` becomes a **fully-fledged programming language in the broadest sense of the word**: a single conceptual continuum bridging pure λ-calculus, symbolic reasoning, macros, typed compilation, machine assembly, and direct physical byte generation for bare-metal targets (x86-64, FPGA, UEFI).

## 2. Парадигма «макро-атомів» / The Macro-Atom Paradigm

### Проблема класичного асемблера
У класичному асемблері (NASM, GAS) розробник або бекенд змушений щоразу вручну виписувати повторювані послідовності інструкцій для найпростіших операцій:
1. Перевірка тегу типу в молодших бітах.
2. Маскування тегу або зсув (untagging).
3. Зсув результату та накладання тегу (tagging).
4. Організація стекового кадру (prologue / epilogue).
5. Виклик алокатора ядра (nucleus allocator) для cons-пари.

У мовах C/C++ або макро-асемблерах текстові макроси є сліпими: вони не знають про типи, не перевіряються оракулом і легко спричиняють колізії регістрів.

### Ліспове рішення: макро-атоми як структуровані комбінації
У Ліспі завдяки гомоіконічності («код як дані») кожна стала комбінація інструкцій стає **макро-атомом**:
* Це не текстовий рядок, а валідне дерево S-виразів.
* Воно параметризується регістрами та зміщеннями.
* Воно може проходити валідацію, семантичний аудит і оптимізацію ще до емісії першого байта.
* Воно розгортається у структурований список інструкцій `MachineInst`.

```text
Високорівневий намір:       (untag-fixnum :rax)
                                    │
                                    ▼ (розгортання макро-атома)
S-вираз асемблера:         (x86:sarq 3 :rax)
                                    │
                                    ▼ (типізований машинний шар)
MachineInst:                MachineInst::SarImm { reg: X86Reg::Rax, imm: 3 }
                                    │
                                    ▼ (кодувальник байтів)
Фізичні байти x86-64:       0x48 0xC1 0xF8 0x03
```

## 3. Каталог базових бібліотек макро-атомів / Core Macro-Atom Libraries

### 3.1. Бібліотека тегування та представлення типів (`lib/asm/tags.lisp`)
Визначає правила представлення даних у 64-бітному слові (Tagging scheme):

* **`tag-fixnum (reg)`**:
  - *Семантика:* Перетворення 61-бітного цілого числа у канонічне 64-бітне значення fixnum (тег `0b001`).
  - *Розгортання x86-64:*
    ```lisp
    `((x86:shlq 3 ,reg)
      (x86:orq 1 ,reg))
    ```
* **`untag-fixnum (reg)`**:
  - *Семантика:* Арифметичний зсув праворуч для отримання чистого машинного значення зі збереженням знаку.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:sarq 3 ,reg))
    ```
* **`check-tag-or-fail (reg tag error_label)`**:
  - *Семантика:* Перевірка молодших трьох бітів слова. Якщо тег не збігається — перехід до обробника помилки або `wsm_fail`.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:movq ,reg %rcx)
      (x86:andq 7 %rcx)
      (x86:cmpq ,tag %rcx)
      (x86:jne ,error_label))
    ```

### 3.2. Бібліотека кадрів виклику та ABI (`lib/asm/abi.lisp`)
Стандартизує роботу зі стеком та виклики процедур відповідно до System V AMD64 ABI:

* **`emit-prologue (frame_size)`**:
  - *Семантика:* Збереження базового вказівника попереднього кадру та виділення локального стекового простору з гарантією 16-байтного вирівнювання.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:pushq %rbp)
      (x86:movq %rsp %rbp)
      (x86:subq ,frame_size %rsp))
    ```
* **`emit-epilogue (frame_size)`**:
  - *Семантика:* Відновлення стеку, регістра `%rbp` та повернення через `ret`.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:movq %rbp %rsp)
      (x86:popq %rbp)
      (x86:ret))
    ```

### 3.3. Бібліотека операцій з пам'яттю та купою (`lib/asm/nucleus.lisp`)
* **`safe-car (dst src error_label)`**:
  - *Семантика:* Перевірка на тег Cons-пари (`0`), читання першого 64-бітного слова за зміщенням `0(%src)`.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:movq ,src %rcx)
      (x86:andq 7 %rcx)
      (x86:jnz ,error_label)
      (x86:movq (disp 0 ,src) ,dst))
    ```
* **`safe-cdr (dst src error_label)`**:
  - *Семантика:* Перевірка на тег Cons-пари, читання другого 64-бітного слова за зміщенням `8(%src)`.
  - *Розгортання x86-64:*
    ```lisp
    `((x86:movq ,src %rcx)
      (x86:andq 7 %rcx)
      (x86:jnz ,error_label)
      (x86:movq (disp 8 ,src) ,dst))
    ```

## 4. Крос-субстратна єдність: x86-64 vs FPGA

Ця архітектура зберігає однакові імена макро-атомів для різних фізичних субстратів. Відрізняється лише фінальне розгортання в цільові інструкції:

| Макро-атом | Намір (Intent) | Розгортання x86-64 | Розгортання FPGA (fpga-lisp ISA) |
|---|---|---|---|
| `(untag-fixnum r)` | Машинне значення числа | `sarq $3, %r` | `GETVAL rd, rs, 1` |
| `(tag-fixnum r)` | Накладання тегу числа | `shlq $3, %r; orq $1, %r` | `MAKEPRIM rd, rs, 1` |
| `(read-timestamp r)` | Апаратний лічильник | `rdtsc; shlq $32, %rdx; orq %rdx, %rax` | `IN rd, 1` (читання таймера) |
| `(call-lisp-fn f)` | Виклик функції | System V ABI call (`%rdi`, `%rsi`...) | Завантаження в `R1`..`R8`, `CALL` |

Таким чином, алгоритми компілятора та системні бібліотеки можуть оперувати **єдиною мовою макро-атомів**, тоді як кодогенератор просто вибирає відповідну таблицю розгортання під цільовий процесор.

## 5. Дорожня карта втілення / Implementation Roadmap

1. **Етап 1 (Завершено в `cml`):**
   - Реалізовано шар `MachineInst` у `src/machine_inst.rs` (регістри, симетричні ALU, Mov/Load/Store, SIB).
   - Підтверджено побайтову ідентичність через оракул системного GNU `as`.
2. **Етап 2 (Наступний крок — DSL макро-атомів):**
   - Описати перший набір макро-атомів для цілі x86-64 у форматі Lisp S-виразів.
   - Забезпечити генерацію зрізу `atom-test` у `wsm-my-lisp` безпосередньо через композицію цих макро-атомів.
3. **Етап 3 (Повний самобутстрап Lisp-асемблера):**
   - Перенести кодувальник `MachineInst -> bytes` у функцію на чистому Ліспі (аналогічно до `assembler.lisp` у `fpga-lisp`).
   - Додати упаковку простого плоского ELF-заголовка (`elf64-x86-64`) засобами Ліспу.
   - Отримати автономний бінарник через `(write-file-bytes "output" ...)`, повністю відмовившись від зовнішнього `as` та `ld`.

## 6. Висновок / Conclusion

Використання Ліспу як власного асемблера на основі структурованих макро-атомів перетворює `my-lisp` на самодостатню систему повного циклу. Це усуває прірву між високорівневою символьною семантикою та фізичною реалізацією в кремнії, надаючи розробнику абсолютний контроль і прозорість на кожному кроці трансляції.
