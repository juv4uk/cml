* **Дата:** 2026-09-14

## 1. Поточний стан та вузькі місця компілятора (Current Bottlenecks)

### Проблема текстової генерації в `x86_freestanding.rs`
Зараз файл `src/x86_freestanding.rs` налічує понад 2,500 рядків коду. Його ядро побудоване на накопиченні рядків:
```rust
self.line(&format!("    movq %rax, {}(%rsp)", Self::slot_offset(slot)));
```

Цей підхід має три фундаментальні проблеми, які ускладнюють розвиток компілятора:

1. **Змішування семантики з розкладкою стека (Stack Layout Entanglement):**
   Вибір інструкцій (`movq`) жорстко прив'язаний до обчислення зміщень на стеку (`slot_offset(slot)`). Якщо нам знадобиться змінити конвенцію виклику або додати регістровий алокатор, доведеться переписати всі 2,500 рядків.
2. **Неможливість валідації до виклику зовнішнього асемблера:**
   Помилка в регістрі, суфіксі чи розмірі операнда проявляється лише тоді, коли GNU `as` повертає помилку парсингу. Компілятор не знає типів операндів.
3. **Залежність від зовнішнього інструменту для розрахунку переходів (Jump Offsets):**
   Текстові мітки на зразок `.L_then_12` скидають усю відповідальність за обчислення відносних зміщень (`rel8` / `rel32`) на зовнішній GNU `as`. Щоб компілятор міг сам видавати байти без GNU `as`, він повинен сам рахувати адреси переходів.

## 2. Пропозиція 1: Декоративна симетрія бінарних операцій (Symmetric ALU Encoding Families)

В архітектурі x86-64 операції базової арифметики та логіки (`ADD`, `OR`, `ADC`, `SBB`, `AND`, `SUB`, `XOR`, `CMP`) утворюють математично досконалу симетричну матрицю:

| Операція | Opcode `r/m64, r64` | Opcode `r64, r/m64` | Immediate Opcode (`/digit`) |
|---|---|---|---|
| **ADD**  | `0x01` | `0x03` | `0x83 /0` (imm8), `0x81 /0` (imm32) |
| **OR**   | `0x09` | `0x0B` | `0x83 /1` (imm8), `0x81 /1` (imm32) |
| **ADC**  | `0x11` | `0x13` | `0x83 /2` (imm8), `0x81 /2` (imm32) |
| **SBB**  | `0x19` | `0x1B` | `0x83 /3` (imm8), `0x81 /3` (imm32) |
| **AND**  | `0x21` | `0x23` | `0x83 /4` (imm8), `0x81 /4` (imm32) |
| **SUB**  | `0x29` | `0x2B` | `0x83 /5` (imm8), `0x81 /5` (imm32) |
| **XOR**  | `0x31` | `0x33` | `0x83 /6` (imm8), `0x81 /6` (imm32) |
| **CMP**  | `0x39` | `0x3B` | `0x83 /7` (imm8), `0x81 /7` (imm32) |

### Що це дає CML:
Замість написання окремих енкодерів і принтерів для кожної інструкції, ми оголошуємо **єдиний шаблон `AluOp`**:
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum AluOp {
    Add = 0,
    Or  = 1,
    Adc = 2,
    Sbb = 3,
    And = 4,
    Sub = 5,
    Xor = 6,
    Cmp = 7,
}

impl AluOp {
    pub fn opcode_reg_reg(self) -> u8 {
        (self as u8) * 8 + 0x01
    }
    
    pub fn modrm_reg_digit(self) -> u8 {
        self as u8
    }
}
```
**Результат:** 8 фундаментальних операцій (64 комбінації регістр-регістр та регістр-immediate) реалізуються в ~40 рядках коду замість 600 рядків ручного форматування рядків.

## 3. Пропозиція 2: Трирівнева модель операндів (3-Level Operand Model)

Щоб назавжди відокремити семантичний вибір інструкцій від конкретного розміщення в пам'яті, пропонується розділити операнди на три фази:

```text
[Рівень 1: Віртуальний операнд під час Target Selection]
  Operand::Reg(X86Reg)
  Operand::Imm(i64)
  Operand::VirtualSlot(SlotId)    <-- компілятор знає тільки логічний номер слота
  Operand::Label(LabelId)         <-- компілятор знає тільки логічну мітку переходу

                 │
                 ▼  (Nanopass: Frame Allocation / Stack Layout)
                 │
[Рівень 2: Фізичний операнд перед емісією]
  Operand::Reg(X86Reg)
  Operand::Imm(i64)
  Operand::Mem { base: X86Reg::Rsp, disp: -16 }
  Operand::ResolvedOffset(i32)

                 │
                 ▼  (Projections)
                 │
  ├───► Projection A: Asm Printer ("movq %rax, -16(%rsp)")
  └───► Projection B: Byte Encoder ([0x48, 0x89, 0x44, 0x24, 0xF0])
```

### Чому це полегшить життя компілятору:
1. `lower.rs` та генератор машинного коду не думають про те, де фізично знаходиться змінна на стеку.
2. Розрахунок червоної зони (`Red Zone`, 128 байт у System V ABI), вирівнювання стека на 16 байт (`align(16)`) та розмір кадру стають **ізольованим мікро-пасом** довжиною в 50 рядків.

## 4. Пропозиція 3: Детерміністичний одноетапний розрахунок переходів (Single-Pass Branch Settling)

Для автономного генератора байтів (без виклику GNU `as`) найбільшою складністю традиційно вважається "розв'язання довжини стрибків" (short jump 2 байти `rel8` проти near jump 5-6 байтів `rel32`).

### Практичне рішення для автономного CML:
1. **Інваріант для умовних переходів у Lisp:**
   У ядрі Lisp (`if`, `cond`, перевірка типів та тегів) 99% переходів локальні (стрибок на кілька інструкцій вперед/назад, менше 127 байт).
2. **Двоетапний прогон без релаксації (Fixed-Size / 2-Pass):**
   * **Пас 1:** Обчислюємо розмір кожної інструкції в байтах (для відомих інструкцій розмір фіксований). Складаємо таблицю `LabelId -> byte_offset`.
   * **Пас 2:** Емітуємо байти, підставляючи точну дельту `target_offset - next_inst_offset`. Якщо стрибок перевищує 127 байт — емітуємо стандартний 32-бітний `0x0F 0x84` (near jz).
3. Це повністю виключає складні ітеративні цикли релаксації та гарантує лінійну швидкість збірки $O(N)$.

## 5. Пропозиція 4: Автоматичний оракул-тест (Differential Oracle Harness)

У Milestone M1 ми запровадили тест `test_byte_encoding_exact_gnu_as_oracle`. Цей підхід треба піднести до рангу системного архітектурного правила:

```text
                 MachineInst
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
    encode_bytes()         print_gnu_asm()
         │                       │
         │ (direct bytes)        │ (asm text)
         │                       ▼
         │                 GNU as + objcopy
         │                       │
         │                       ▼
         │                 (oracle bytes)
         │                       │
         └───────────┬───────────┘
                     ▼
             assert_eq!(direct, oracle)
```

**Перевага:** Жодна інструкція не потрапляє в кодову базу, якщо її бітова структура не верифікована незалежним системним асемблером. Це гарантує, що коли ми відключимо GNU `as` у production, байткод компілятора працюватиме 100% ідентично на реальному залізі.

## 6. Рекомендований план наступних кроків (Next Steps Roadmap)

1. **Крок 1 (Семантичний handoff від `my-lisp`):**
   Отримати від Vova формальний семантичний контракт для `read-cycle-counter` (істинна семантика, арність 0, volatile observation, error kind).
2. **Крок 2 (Розширення `MachineInst` на базові операції):**
   Впровадити `AluOp` (`add`, `sub`, `and`, `or`) та базовий `Mov` (регістр-регістр, регістр-пам'ять).
3. **Крок 3 (Переведення всього `x86_freestanding` на генерацію `Vec<MachineInst>`):**
   Заміна рядкових `self.line(...)` на типізовані `MachineInst`. На цьому кроці вихідний код продовжує друкуватися у текстовий `.s` через `print_gnu_asm()`, що зберігає повну сумісність з існуючими тестами та QEMU UEFI образом.
4. **Крок 4 (Повна автономія тулчейну):**
   Додавання генератора плоского бінарного образу (або простого ELF/PE) безпосередньо з байтів `MachineInst::encode_bytes()`. CML стає повністю самостійним компілятором, здатним напряму створювати виконуваний код для ОС.
