## 1. Модель SBCL VOPs (Virtual Operations)

### Що це таке?
В SBCL проміжне представлення другого рівня (IR2) не складається з абстрактних інструкцій процесора або неструктурованих рядків асемблера. Його одиницею є **VOP (Virtual Operation)** — рецепт генерації коду, який пов'язує семантичну операцію Lisp із машинними інструкціями.

### Структура `define-vop`
Кожен VOP декларативно описує:
* **`:translate`** — з якою семантичною функцією Lisp пов'язана операція (наприклад, `+`, `aref`, `read-cycle-counter`).
* **`:args` та `:results`** — входи й виходи з визначенням **Storage Classes (SC)** (класів зберігання): чи очікується операнд у регістрі цілих чисел, на стеку, у плаваючому регістрі чи як immediate-константа.
* **`:arg-types` та `:result-types`** — типи мови (наприклад, `fixnum`, `unsigned-num`), що дозволяє спеціалізувати код без зайвого рантайм-пакування.
* **`:generator`** — тіло емісії, яке використовує макроси інструкцій `(inst ...)`.

Приклад типового VOP:
```lisp
(define-vop (fast-fixnum-add)
  (:translate +)
  (:args (x :scs (any-reg) :target r)
         (y :scs (any-reg)))
  (:arg-types tagged-num tagged-num)
  (:results (r :scs (any-reg)))
  (:result-types tagged-num)
  (:generator 2
    (inst mov r x)
    (inst add r y)))
```

### Урок для нашого CML та `MachineInst`:
1. **Storage Classes (SC)** — це саме те, що розрізняє віртуальні та фізичні операнди.
2. VOP доводить, що **семантичний контракт та правила генерації мають бути розділені, але зв'язані через декларативне відображення (`:translate`)**.
3. Наші **макро-атоми** в Ліспі є природним, але значно більш легким і прозорим еквівалентом VOP: вони оперують S-виразами над `MachineInst` без монструозного апарату SBCL IR2.

## 2. Дисципліна Nanopass (Chez Scheme)

### Головний принцип
Фреймворк Nanopass (створений Кентом Дібвігом та Енді Кіпом, покладений в основу Chez Scheme) відкидає ідею монолітних компіляторних пасів. Замість 3-4 гігантських проходів компілятор будується з **50–80 мікро-пасів** (nanopasses).

Кожен пас робить рівно одну трансформацію над строго типізованою мовою:
$$L_{\text{source}} \longrightarrow L_{\text{macros}} \longrightarrow L_{\text{core}} \longrightarrow L_{\text{normalized}} \longrightarrow L_{\text{target-neutral}} \longrightarrow L_{\text{machine-inst}} \longrightarrow L_{\text{bytes}}$$

### Уроки для instruction selection:
* **Експліцитні обмеження архітектури (Constraint Enforcement):**
  Наприклад, в архітектурі x86-64 операція додавання або копіювання не може одночасно мати операндом пам'ять і в джерелі, і в призначенні (`mov [rsp], [rbp]` — заборонено). У Nanopass є окремий мікро-пас, який виявляє такі неможливі комбінації й примусово інжектує тимчасовий регістр.
* **Паттерн-матчинг замість if-else каскадів:**
  Вибір інструкцій виконується як просте перезаписування дерева за зразком.
* **Контроль YAGNI:**
  Не додавати новий рівень мови або проміжне представлення, доки немає конкретного інваріанта, який неможливо виразити на поточному кроці.

## 3. Уроки Mezzano: «Lisp All the Way Down» на голому залізі

### Досягнення Mezzano
Mezzano — це операційна система, повністю написана на Common Lisp, що завантажується безпосередньо через UEFI / BIOS на x86-64 (а також AArch64) без будь-якого Linux, C чи стороннього рантайму.

### Ключові інженерні рішення:
1. **Unboxed Value Representations:**
   У звичайних Lisp-системах будь-яке число часто загортається в об'єкт на купі (boxed). Mezzano реалізує SSA-компілятор, який для цілочисельної арифметики (`unsigned-byte 64`) та локальних змінних працює з «голими» машинними регістрами без накладання тегів, тегуючи значення лише при виході в динамічний контекст.
2. **Власний Lisp-асемблер та `DISASSEMBLE`:**
   Компілятор Mezzano містить власний кодувальник інструкцій x86-64, написаний на Ліспі. Будь-яка скомпільована функція може бути дезасембльована прямо в системному REPL.
3. **Автономний ELF / бінарний бутстрап:**
   Mezzano довів практичну можливість генерації виконуваних машинних структур (сторінок пам'яті з прапорцем виконання) безпосередньо за допомогою Lisp-функцій запису слів у масив.

## 4. CakeML: Формально верифікована емісія байтів

### Суть підходу
Проєкт CakeML (University of Cambridge / Chalmers) створив повний стек від функційної мови до машинного коду, де кожна інструкція верифікована в інтерактивному доводчику теорем HOL4.

### Що ми можемо перейняти без формального тягаря HOL4:
1. **Оракул-еквівалентність (Oracle Equivalence):**
   CakeML доводить еквівалентність математично; ми у `cml` доводимо еквівалентність **експериментально-диференційним оракулом** (`test_byte_encoding_exact_gnu_as_oracle`):
   $$\text{CML direct bytes} \equiv \text{GNU as assembled bytes}$$
2. **Deterministic byte generation:**
   Емісія байтів є строго чистою математичною функцією від структури `MachineInst` без випадкового стану або невизначених паддінгів.

## 6. Практичні висновки для поточної гілки компілятора

1. **Впровадити Storage Classes (SC) у `MachineInst`**:
   Додати чітке розрізнення операндів:
   - `Reg(X86Reg)` — фізичний регістр;
   - `StackSlot(i32)` — зміщення від `%rsp`;
   - `Imm(i64)` — пряме числове значення.
   Це дозволить валідатору заздалегідь відхиляти заборонені комбінації x86 (пам'ять-пам'ять).

2. **Формат макро-атомів у стилі легких VOPs**:
   Макро-атоми (`tag-fixnum`, `safe-car`, `read-timestamp`) повинні мати чітко задекларовані очікування щодо операндів, щоб компілятор знав, які регістри використовуються як тимчасові (clobbered/scratch).

3. **Синтез плоского ELF заголовка**:
   Наступним важливим кроком після кодування інструкцій є створення мінімальної структури ELF64 (заголовок ELF + Program Header + секція `.text`), що дозволить Ліспу записувати безпосередньо виконувані файли для Linux без виклику системного компонувальника `ld`.
