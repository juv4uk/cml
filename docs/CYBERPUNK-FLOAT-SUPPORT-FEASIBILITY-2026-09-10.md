# Дослідження: чи має cml підтримку float/non-integer числових значень

**Автор:** cml-1
**Дата:** 2026-09-10
**Статус:** дослідження (feasibility), НЕ реалізація

## Питання

Якщо колись знадобиться AOT-компіляція скрипта, що читає float-значення
(наприклад, позицію гравця з гри) — чи має cml підтримку float/non-integer
numeric представлення в IR?

## Метод

Прочитав реальний код `parser.rs`, `ast.rs`, `lower.rs`, `ir.rs`,
`c_backend.rs`, `semantic.rs`, і реальні тести (`decimal_separator_test.rs`).
Не здогадувався — перевірив кожне твердження нижче в коді.

## Головний, найважливіший висновок

**У cml (і в мові my-lisp, яку він компілює) НЕМАЄ scalar-float як типу
джерела взагалі.** Це не прогалина реалізації — це навмисний семантичний
вибір мови: my-lisp за замовчуванням exact (точний), не inexact.

Перевірено напряму (`ast.rs`): немає жодного варіанта `Expr::Float`. Числові
десяткові літерали з крапкою чи комою (`12.455`, `12,455`) **не** стають
IEEE-754 float — вони парсяться в **точний Rational**:

```
"12.455" -> Expr::Rational(2491, 200)   // не binary32/64!
"0.5"    -> Expr::Rational(1, 2)
"1.5e3"  -> Expr::Integer(1500)         // ціле, бо результат точний
```

Тобто позиція гравця `123.45`, записана прямо в джерельному коді cml, стала б
точним раціональним `2469/20`, не lossy binary-float.

## Де IEEE-754 float все ж таки існує (і чому це не рятує ситуацію)

`Ir::Float(f64)` і `Quoted::Float(f64)` **існують** в `ir.rs`, і `#f32(1.0
2.0 3.0)` **є** реальним, парсованим синтаксисом (`parser.rs`) — але лише як
**buffer-літерал для GPU compute kernels** (Compute IR / `NumericBufferLiteral::F32`),
не як scalar-значення. І цей шлях **явно й повсюдно відхилений** на
семантичному рівні:

```rust
// semantic.rs, реальний, активний тест:
fn rejects_f32_numeric_buffer() { ... assert_eq!(error.kind, UnsupportedF32Buffer); }
```

Перевірив усі бекенди — жоден не приймає F32:
- `c_backend.rs`: `Ir::Float(_) => Err(UnsupportedVariant("Float"))`,
  `Buffer(F32(_)) => Err(UnsupportedTypedBuffer)`.
- FPGA/`compiler.rs`, `x86_freestanding.rs`: та сама відмова (перевірено в
  `exhaustive_classification_test.rs` — обидва explicitly rejects Float).
- GPU-бекенди (`gpu_cuda_test.rs`, `gpu_wgsl_test.rs`): той самий
  `UnsupportedF32Buffer`, навіть там, де компіляція в CUDA/WGSL технічно
  можлива — семантичний гейт блокує це раніше.

`Ir::Float`/`Quoted::Float` фактично існують у коді лише для повноти
exhaustive-match тестів (`exhaustive_classification_test.rs`,
`ir_classification_matrix_test.rs`, які конструюють `Ir::Float` синтетично
в Rust) — жоден реальний парсований вираз джерельного коду ніколи не
породжує `Ir::Float` (`lower.rs` не має жодного правила `Expr -> Ir::Float`,
бо немає `Expr::Float`, з якого ловерити).

## Практичний висновок для Cyberpunk-теми

Якщо мод-скрипт колись муситиме прочитати `player-position` як float:

1. **Не можна** записати float-літерал прямо в cml-джерелі — така синтаксична
   форма не існує (десяткові числа стають точними Rational).
2. **Можна** передати float-значення ЗЗОВНІ (через host-capability виклик,
   той самий `wsm_*`-import-механізм з попереднього дослідження) — але
   значення прийде як **опакове** слово, яке cml не зможе інтерпретувати як
   число (жоден бекенд не декодує f64/f32 з тегованого слова).
3. Практичний шлях без чекання на нову мовну фічу: host-функція
   (`wsm_player_position_x` абощо) повертає **вже round-трипнуте точне
   значення** — наприклад, ціле число в сантиметрах/мілі-одиницях, або
   Rational, замість сирого binary-float. Це рішення на боці
   RED4ext-адаптера/runtime, не cml — cml просто споживає те число, яке
   отримає, і exact-числова арифметика (`+`/`-`/rational) уже повністю
   робоча.
4. **Справжня** підтримка binary-float у cml-скриптах — це велика, окрема,
   свідомо відкладена робота (потрібно: рішення my-lisp додати inexact-тип
   у мову семантично, потім cml IR/lowering, потім кожен бекенд). Не
   рекомендую починати це заради Cyberpunk-теми конкретно — простіше й
   безпечніше конвертувати float у exact на боці host-адаптера один раз,
   ніж проносити inexact-арифметику через увесь стек.

## Підсумок

cml не готовий до float у жодному сенсі, і причина не "ще не встигли" — це
навмисний вибір мови (exact-by-default). Найпрактичніший шлях для
Cyberpunk-даних з плаваючою комою — конвертувати їх в exact-представлення
(ціле чи Rational) на межі host-адаптера, до того, як значення взагалі
потрапляє в Lisp-бік. Реалізація тут не потрібна й не рекомендується зараз.
