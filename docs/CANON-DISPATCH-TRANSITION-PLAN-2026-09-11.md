# План переходу на канон+таблиці функцій: numeric-ID dispatch замість hardcoded написання

**Автор:** cml
**Дата:** 2026-09-11
**Статус:** ЛИШЕ документ-план, жодної реалізації

## Мета

Показати, як усі споживачі `semantic-registry.wsm` (my-lisp, wsm-my-lisp, cml, fpga-lisp)
мали б диспетчеризувати через канонічні числові ID замість hardcoded написання чи
uppercasing-based rewriting -- і чесно розібрати, чи знахідка `radio`/`RADIO`-злиття
є прикладом цієї самої категорії бага, чи іншої.

## Головний, найважливіший висновок наперед

**`radio`/`RADIO`-злиття НЕ виправляється цим планом.** Це не помилка розпізнавання
Canon-форми (як cml#9's Знахідка 1) -- це зовсім інша, окрема проблема. Розбираю
обидві категорії нижче окремо, з чесним поясненням, чому пропонований механізм
вирішує одну, але не іншу -- і що реально вирішило б другу.

## Категорія 1: розпізнавання Canon-форм (quote/cond/lambda/def/...)

**Симптом:** `lower.rs` розпізнає спецформи лише за англійським написанням:

```rust
"quote" if args.len() == 1 => ...
"cond" => ...
"lambda" if args.len() >= 2 => ...
"def" if args.len() == 2 => ...
```

Джерело з `як-є`/`за-умовою`/`функція`/`визначити` НЕ розпізнається як спецформа
взагалі -- падає в generic App-виклик до невідомого символу.

**Чому numeric-ID dispatch вирішує САМЕ ЦЕ:** Canon-форми -- це закритий, фіксований
набір (0001-0012 у реєстрі), кожен ID має кілька рівноправних написань (en/uk/sa/sym).
Задача розпізнавання тут -- "чи це ОДНА З ЦИХ конкретних N форм, під будь-яким її
написанням?" Це природно вирішується таблицею відповідності (написання -> canon ID),
згенерованою з реального реєстру -- саме той механізм, який `build.rs` (cml#9,
коміт 26e20e7) уже реалізує для `semantic.rs`'s reserved-name перевірки.

**Розширення на `lower.rs`:** той самий генератор може додатково породити
`SPECIAL_FORM_BY_SURFACE: &[(&str, u32)]` (написання -> canon ID) для ID
0001/0007/0010/0011/0012 (quote/cond/lambda/define/defmacro -- ті, що `lower.rs`
реально розпізнає як спецформи). `lower_expr` тоді питає не `head.as_str() == "cond"`,
а "чи `head` відповідає canon ID 0007 у будь-якому написанні?", і диспетчеризує за
ID, не за рядком:

```text
Джерело: (за-умовою (test1 body1) (test2 body2))
              |
    lookup(surface="за-умовою") -> canon ID 0007
              |
    dispatch on numeric ID 0007 -> lower_cond(...)
```

Це прямо закриває cml#9's Знахідку 1: одна таблиця, згенерована з реального реєстру,
а не 12+ hardcoded рядкових порівнянь для кожного написання кожної форми.

## Категорія 2: `radio`/`RADIO`-злиття -- ІНША проблема, не canon-dispatch

**Симптом:** `(eq (quote radio) (quote RADIO))` компілюється й виконується в `T`
(перевірено емпірично, коміт-контекст fpga-lisp-2e/my-lisp-5b обміну).

**Чому це НЕ те саме, що Категорія 1:** `radio` -- не canon-форма. Це довільний,
визначений користувачем символ (дані програми), якого НЕМАЄ і ніколи не буде в
`semantic-registry.wsm` -- реєстр покриває закриту множину МОВНИХ примітивів/спецформ,
не довільні символи-дані з джерела користувача. Таблиця відповідності (написання ->
canon ID), яка вирішує Категорію 1, просто НЕ МАЄ запису для `radio` -- вона не
призначена для цього і не повинна бути.

**Справжня причина злиття:** окремий, значно ширший механізм -- `lower.rs`'s
`lower_quoted` uppercase-ить КОЖЕН quoted-символ безумовно:

```rust
// src/lower.rs:456
Expr::Symbol(s) => Ok(Quoted::Sym(s.to_uppercase())),
```

Це та сама uppercasing-конвенція, яку cml застосовує до BINDER-імен (параметри
лямбди, імена `def`, рядки 241/287/387/390/399/422/441) -- де вона СТРУКТУРНО
необхідна: ці імена стають реальними target-ідентифікаторами (C-змінні,
fpga-lisp asm-мітки), а цільова мова/асемблер має свою власну конвенцію іменування.
Але `lower_quoted`'s випадок -- це не ім'я-ідентифікатор, це ЗНАЧЕННЯ-СИМВОЛ (дані,
які порівнюються через `eq`/`equal?`), і застосування ТІЄЇ Ж конвенції до даних
безпідставно змішує дві різні речі.

**Прецедент, який уже існує в cml для точно такого ж класу проблеми:** commit
0252110 (issue-independent, раніше ця сесія) виправив ідентичну помилку для
quoted-рядків -- `Quoted::Str` колись теж uppercase-ився так само, як символ-ідентифікатор,
хоча вміст рядка -- це користувацькі дані, не target-ім'я. Фікс був: `s.clone()`
замість `s.to_uppercase()`. Той самий аргумент, слово в слово, застосовується до
`Quoted::Sym` у `lower_quoted` (не до символів-БАЙНДЕРІВ, лише до символів-ЗНАЧЕНЬ
усередині `quote`).

## Підсумкова таблиця: що яка проблема, і що її вирішує

| Проблема | Приклад | Categorтя | Вирішується numeric-ID таблицею? | Реальний фікс |
|---|---|---|---|---|
| Canon-форма не розпізнана | `за-умовою` не працює як `cond` | 1: закритий набір мовних форм | Так -- build.rs-генератор, за прецедентом cml#9 | Таблиця (написання -> canon ID) з реального реєстру |
| Символи-дані зливаються за регістром | `radio` == `RADIO` | 2: довільні user-symbols, поза реєстром | Ні -- вони не в реєстрі й не мають бути | Case-preserving `Quoted::Sym` (той самий фікс, що вже зроблено для `Quoted::Str` у 0252110) |

## Рекомендований порядок робіт (лише план, не зараз)

1. **Категорія 2 спершу, вона простіша й ізольованіша:** змінити `lower_quoted`'s
   `Expr::Symbol` на case-preserving, за прецедентом `Quoted::Str`. Це вимагає
   ratified рішення (не одноосібне -- впливає на те, як my-lisp/fpga-lisp порівнюють
   compiled символи з оракулом), але сам фікс механічно тривіальний.
2. **Категорія 1 після:** розширити `build.rs` (cml#9) на генерацію
   `SPECIAL_FORM_BY_SURFACE` для `lower.rs`, перевести `lower_expr`'s spec-form
   dispatch з рядкових порівнянь на canon-ID lookup.
3. **Не змішувати два фікси в один PR/коміт** -- вони вирішують структурно різні
   проблеми з різними ризик-профілями (2 -- чиста семантика значень, 1 -- зміна
   dispatch-механізму спецформ).

## Що це НЕ вирішує (свідомо поза межами)

- Binder-імена (параметри, `def`-імена) залишаються uppercased -- це необхідна
  target-namespace конвенція, не помилка.
- lambda/define/defmacro (0010/0011/0012) як binder-форми в `semantic.rs`'s
  reserved-name перевірці -- окреме, ще не досліджене питання (cml#9 коментар).
- Жодна зміна в цьому документі не торкається fpga-lisp/wsm-my-lisp кодових баз --
  лише cml-side dispatch-механізм.
