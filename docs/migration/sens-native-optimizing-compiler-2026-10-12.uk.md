# SENS: власний оптимізувальний компілятор за архітектурною ідеєю SBCL

**Дата:** 12.10.2026. **Статус:** робочий кандидат O1, **не** випуск native-компілятора.
Цей документ описує власну архітектуру **SENS → CML**, а не
Common Lisp або SBCL-совмісний фронтенд. Жоден двійковий домен
не виводиться зі старого SID8 чи з написання поверхневого імені.

## Що беремо з SBCL, а чого НЕ беремо

SBCL — досвідчений оптимізувальний Common Lisp-компілятор:
розділення проміжного представлення, аналіз типів, компіляторна
політика, спеціалізовані низькорівневі операції (VOP), а також
компроміс швидкість/простір/безпека. Це **інженерний донор**,
не мовна норма SENS. Офіційна документація:
- https://www.sbcl.org/manual/ — compiler, open coding, type safety;
- https://www.sbcl.org/ — версія і загальна архітектура;
- https://github.com/sbcl/sbcl/tree/master/src/compiler — реальна реалізація.

Для дослідження наступних оптимізацій корисні e-graph / equality saturation:
https://doi.org/10.1145/3815481 (CACM, 2026), але це не
дозвіл автоматично переписувати все: кожний переписаний вираз
потребує **власного закону SENS** і перевірки ефектів/помилок,
а сучасні дослідження також показують ризик unsound analysis
у циклічному SSA (https://doi.org/10.1145/3808302, 2026).

## Наш власний конвеєр

1. **Фізична влада:** тільки канонічний T5 `.sens`; оригінальна
   F3 `.senc` — лише явна, крихітна, з довіреним SHA-256
   *фізичних* байтів до декодування. F3 → точний T5, жодного
   auto-detection або виправлення байтів за здогадом.
2. **Семантична влада:** D2 parser + ratified Dn-виклики, точна
   ширина, `compiler_semantic_input_from_sens`, доказовий ref,
   SHA-256 `language-contract.lisp`. Усі такі запити здійснює
   **сам SENS**. CML не підтримує другу таблицю значень.
3. **Точний AST/IR:** [кореневий файл](../../src/current_exact_model.rs)
   несе `VerifiedRole`, `ExactQuotedData`, `ModernAst`, `ModernIr`.
   Цитований вираз є **даними**, не рекурсивною програмою; binder/locals,
   незатверджені домени й залишкові виклики не проходять без
   доведеного семантичного контракту.
4. **Оптимізатор O0/O1:** [власний модуль](../../src/current_exact_optimizer.rs).
   O0 = перевірка структури без переписування. O1 = лише
   `HEAD(PAIR(QUOTE a,QUOTE b)) → QUOTE a` і
   `TAIL(PAIR(QUOTE a,QUOTE b)) → QUOTE b`.
   В обох випадках жоден із двох аргументів не має неперевірених
   ефектів: обидва є цитованими даними. **Загальний**
   `HEAD(PAIR(expr,expr)) → expr` заборонений, бо міг би
   прибрати оцінювання другого аргумента.
5. **Ціна і сертифікат:** поточна метрика — **кількість вузлів IR**,
   а не фактична швидкість CPU/GPU. Кожен rewrite має точні
   ідентичності Dn, SHA закону, `before/after` і прив'язку до
   SHA-256 незмінного оригінального T5. Свідчення — це
   *перевірюваний журнал*, не формальний доказ загальної
   еквівалентності.
6. **Суворий replay з первинного носія:** див.
   `replay_optimizer_witness_from_t5(original_bytes, candidate)`.
   Фізичний T5 перевіряється з нуля, оптимізація повторюється
   детерміновано, порівнюється **увесь** `OptimizedProgram`.
   Підміна digest, IR, іншої програми або сертифіката має давати
   відмову. Для семантичного допуску O1 додатково є незалежні
   диференційні тести SENS: два правила × чотири типи цитованих
   даних × парні комбінації = **32 перевірки**.
7. **Native backend:** окремий етап після повної міграції
   `Expr::Sid/Ir::Sid`, бекендів і нативного оракула.
   Зелений O1 IR **не доводить** швидкість і правильність
   машинного коду. CPU, FPGA, CUDA/GPU потребують власних
   позитивних і негативних свідчень.

## Правила розширення

- Кожне нове правило — окремий **law ID**, передумови щодо
  типу/ефектів і точних доменів, negative tests, випробування
  з реальною SENS-оцінкою, звіт про обсяг тестованих форм.
- Перевірка `COND`, `ATOM`, `EQ`, числа, побічні ефекти і
  невизначеність **не** можуть спиратися на Common Lisp.
  Особливо не можна прибирати `COND`-гілки або eager аргументи
  без підтвердження, що це не змінить помилки/ефекти.
- Можливі майбутні кроки: константна абстрактна інтерпретація
  з proof-gated ефектами, SSA для відомих чистих місць,
  source-validated e-graphs із обмеженням вузлів і часу,
  cost models для x86/FPGA/GPU **після** oracle parity.
- Жодних нових гілок Git, старого SID8 як авторитету, тихих
  text fallback, фальшивого PASS або автоматичного
  перемикання виробничого SENS gitlink.

## Відтворення

```sh
cargo test --manifest-path integration/current-sens-transport/Cargo.toml -- --nocapture
cargo run --manifest-path integration/current-sens-transport/Cargo.toml \
  --bin optimize_exact -- --t5 path/to/program.sens
```

SENS-кандидат має бути закріплений за
`390f313242b538cb954dc00afa32ef0003f7d94b` і пройти
його власний компіляторний закон. Для F3:
`--f3 file.senc TRUSTED_64_HEX_SHA256`.

**Докази:** [наявний зелений O1 CI](https://github.com/juv4uk/cml/actions/runs/38191468100);
[корпус 32 rewrite-випадків](../../integration/current-sens-transport/tests/optimizer_quoted_pairs_matrix.rs);
[перевірка source-owned replay](../../integration/current-sens-transport/tests/optimizer_physical_attestation.rs).

Проміжний висновок: не «SBCL на двійкових символах», а **самостійний
SENS-компілятор, де закони мови і фізичні двійкові коди визначають
допустимі оптимізації, а CML лише здійснює механізм виконання**.
