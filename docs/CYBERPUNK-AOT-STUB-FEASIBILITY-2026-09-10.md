# Дослідження: чи придатний x86_64/C-бекенд cml для extern "C" ABI wsm-my-lisp

**Автор:** cml-1
**Дата:** 2026-09-10
**Статус:** дослідження (feasibility), НЕ реалізація

## Задача

Оцінити, чи можна взяти вже наявний C-бекенд cml (`src/c_backend.rs`) і/або x86_64-бекенд
(`src/x86_freestanding.rs`) і згенерувати нативний stub, сумісний з ABI, який wsm-my-lisp
узгодив для Cyberpunk-моддингу: `wsm_session_init` / `wsm_register_primitive` / `wsm_bind` /
`wsm_eval_string`.

## Метод

Прочитав реальний код `src/c_backend.rs` (не документацію) — механізм `compile_program`,
структуру рантайму (`Value`, `global_env`, `bind_global`, `bootstrap_builtins`), і
`docs/x86-freestanding-backend.md` для другого бекенду. Висновки нижче ґрунтуються на
прочитаному коді, не на здогадках про архітектуру.

## Що вже підходить (реально, без змін)

`c_backend.rs`'s рантайм уже має саме ту форму даних, яка потрібна для host-callback
реєстрації:

```c
static Value *global_env = &NIL_V;

static void bind_global(const char *name, Value *value) {
    global_env = mk_cons(mk_cons(mk_sym(name), value), global_env);
}

static Value *mk_builtin(const char *name, Value *(*fn)(Value*, Value*));
```

Це вже точнісінько механізм `wsm_register_primitive`/`wsm_bind` — просто внутрішній,
не експортований назовні. `bootstrap_builtins()` викликає `bind_global` для кожного
вбудованого примітива (`+`, `cons`, `car`, ...) тим самим способом, яким мав би працювати
host-виклик.

**Висновок:** `wsm_register_primitive(name, fn)` → тонка `extern "C"`-обгортка над
`bind_global(name, mk_builtin(name, fn))`. `wsm_bind(name, value)` → пряма обгортка над
`bind_global`. Обидві функції — це буквально 2 рядки коду поверх наявного механізму, не
нова архітектура.

## Що потребує реальної роботи (не тривіально)

**`wsm_session_init`** — зараз `global_env` є єдиним процес-широким `static`, не полем
якогось контексту. Для справжньої мульти-сесійності (кілька ізольованих Lisp-середовищ в
одному процесі) це потребує рефакторингу: обгорнути `global_env` у структуру-хендл, яку
`wsm_session_init` створює і повертає, а всі інші виклики (`bind_global`, `env_lookup`,
компільовані `Def`) приймають як параметр замість глобальної змінної. Помірний, але не
тривіальний рефакторинг — торкається практично кожної функції рантайму.

Якщо реальний use-case — один ігровий процес, одна Lisp-сесія (що правдоподібно для
Cyberpunk-мода), `wsm_session_init` міг би бути спрощений до no-op/one-shot виклику
`bootstrap_builtins()` — але це свідоме спрощення, яке варто явно задокументувати як
припущення, а не мовчки видати за повноцінну сесійність.

## Що НЕ підходить структурно -- і чому

**`wsm_eval_string` -- це не задача cml, і не буде задачею cml без зміни архітектури.**

`compile_program` у `c_backend.rs` генерує єдиний фіксований `int main(void)` -- парсинг
відбувається один раз, під час компіляції, в Rust (`parser::parse`), ДО того, як хоч рядок
C-коду існує. У згенерованому C-рантаймі **немає рідера** -- жодного парсера s-виразів,
жодного tree-walking evaluator для довільного рядка. `wsm_eval_string("(teleport player 100 200 50)")`
вимагає прочитати й обчислити текст ПІД ЧАС виконання гри -- це категорично інша модель,
ніж AOT-компіляція (compile-once, run-fixed-shape), яку cml реалізує.

Щоб підтримати `wsm_eval_string` у C-бекенді, довелося б з нуля написати повноцінний
C-рідер+евалюатор -- фактично продублювати роботу, яку my-lisp/wsm-my-lisp вже роблять
у своєму нуклеусі/евалюаторі. Це не "бракуюча фіча", це інша програма.

x86_freestanding.rs -- та сама історія, ще й гірше для цього use-case конкретно: точка
входу фіксована (`wsm_entry(RuntimeContext*)`, одна на скомпільовану одиницю, без назви),
SysV AMD64-калінг-конвенція (Win64 ще не підтверджено), і взагалі без libc/syscalls --
призначався для wsm-os-lisp (ОС-ядро), не для host-injected DLL.

## Підсумок і рекомендація

| ABI-функція | Стан у cml |
|---|---|
| `wsm_register_primitive` | Тривіальна `extern "C"`-обгортка над наявним `bind_global`+`mk_builtin` |
| `wsm_bind` | Тривіальна `extern "C"`-обгортка над наявним `bind_global` |
| `wsm_session_init` | Потребує помірного рефакторингу (`global_env` -> поле хендла), АБО свідомо спрощується до one-shot для однопроцесного use-case |
| `wsm_eval_string` | **Не задача cml.** Вимагає рантайм-рідер+евалюатор -- це домен my-lisp/wsm-my-lisp, не AOT-компілятора |

Реалістичний внесок cml у цю ABI: `wsm_register_primitive`+`wsm_bind` -- дешево і вже
майже готово в наявному C-рантаймі. `wsm_session_init` -- вартий обговорення масштабу
(one-shot vs справжня мульти-сесійність) ДО реалізації. `wsm_eval_string` -- залишається
повністю поза cml; я НЕ пропоную братися за це.

Це дослідження, не реалізація -- нічого з описаного вище ще не написано в
`src/c_backend.rs`.
