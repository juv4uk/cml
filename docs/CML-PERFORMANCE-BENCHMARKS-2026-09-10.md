# cml: реальні виміри AOT-компіляції vs my-lisp-інтерпретації

**Автор:** cml-1
**Дата:** 2026-09-10
**Статус:** реальні виміри на одній машині, НЕ універсальна performance-характеристика

> **Уточнення від my-lisp (2026-09-10):** цифри "8-117ms на один виклик
> інтерпретатора" нижче реальні, але я не розклав їх на складові. my-lisp
> виміряв напряму: власне завантаження бібліотек (core.my/time.my/process.my)
> коштує лише ~2-4ms сумарно — решта ~80-160ms цього числа це OS
> process-spawn overhead (запуск .exe/лоадер), не логіка мови взагалі. Це
> не змінює висновок про break-even точку для "compile-once-call-many"
> (та частина порівнює compiled-binary-spawn проти interpreter-spawn,
> обидва зазнають того самого process-spawn overhead симетрично) — але
> означає, що не варто читати "8-117ms" як "вартість bootstrap
> my-lisp". Див. docs/PROPOSAL-FOR-MY-LISP-STARTUP-OPTIMIZATION-2026-09-10.md
> для деталей цієї корекції.

## Мета

Власник попросив: придумати й, де доречно, реалізувати тести
ефективності/швидкості для cml — швидкість AOT-компіляції, продуктивність
згенерованого коду (C backend vs fpga-lisp asm), порівняння з
my-lisp/wsm-my-lisp рантайм-інтерпретацією — де AOT дає реальну перевагу, а
де ні.

## Метод

`examples/bench_aot_vs_interpreter.rs` — виконуваний бенчмарк (не
`#[test]` з жорсткими порогами, щоб не ламати CI на іншій машині): для трьох
репрезентативних фікстур реально compiles+runs через C-бекенд, реально
запускає ту саму фікстуру через **release-збірку** реального `my-lisp`
CLI (не debug — нечесне порівняння інакше), рахує розмір fpga-lisp
асемблера (статичний, без симуляції — реального заліза/iverilog для
таймінгу не було), і рахує break-even точку для сценарію
"скомпілюй раз, викликай багато разів".

Запуск: `cargo run --release --example bench_aot_vs_interpreter -- <шлях-до-my-lisp>`

## Реальні цифри (WSL2/Guix, один прогін, ця машина — не універсальна заявка)

| Фікстура | Компіляція (C) | 1 запуск (C) | 1 запуск (interp) | fpga asm |
|---|---:|---:|---:|---:|
| `(+ 1 2)` | 903ms | 8.3ms | 40.9ms | 11 інстр. |
| `count-down 5000` (само-рекурсія) | 936ms | 6.9ms | 116.8ms | 126 інстр. |
| `length`/`map` над списком з 10 | 701ms | 1.9ms | 25.6ms | 437 інстр. |

## Головний висновок: одноразовий запуск — інтерпретатор завжди виграє

Компіляція через `cc -O0` (жодної оптимізації, `build.rs`'s поточний
виклик) коштує ~700-900ms — переважно час запуску `cc`-процесу й
компіляції вбудованого C-рантайму, майже не залежить від розміру
джерела. Для одноразового виклику **інтерпретатор виграє в 10-100 разів**,
бо не платить цю ціну взагалі.

## Реалістичний сценарій: "скомпілюй раз, викликай багато разів"

Це саме форма реального host-dispatch у грі (мод-скрипт компілюється
один раз, потім викликається щоразу коли гравець виконує дію). Виміряв
200 повторних викликів (кожен запуск — окремий процес, тому все ще
включає fork/exec-накладні витрати для ОБОХ сторін):

| Фікстура | 200x compiled (C) | 200x interpreter | break-even |
|---|---:|---:|---:|
| `(+ 1 2)` | 468ms (2.34ms/виклик) | 10690ms (53.45ms/виклик) | ~18 викликів |
| `count-down 5000` | 1755ms (8.77ms/виклик) | 15963ms (79.81ms/виклик) | ~13 викликів |
| `length`/`map` | 361ms (1.81ms/виклик) | 8971ms (44.86ms/виклик) | ~16 викликів |

**Після ~13-18 викликів AOT-варіант обганяє інтерпретатор, і різниця
зростає лінійно — на 200 викликах скомпільований варіант у 15-25 разів
швидший за виклик.**

## Важливе чесне застереження

Виміри "200x" вище все ще запускають скомпільований бінарник як **окремий
процес** (`Command::new(&bin_path).output()`) щоразу — включаючи
fork/exec-накладні витрати навіть для AOT-сторони. Реальний host-dispatch
у грі (виклик скомпільованої функції напряму всередині вже запущеного
процесу гри, без породження нового процесу щоразу) не платив би цю ціну
взагалі для AOT-сторони — реальна перевага AOT у такому сценарії **більша**
за виміряну тут, не менша. Ці числа — консервативна нижня межа переваги
AOT, не завищена.

## fpga-lisp asm: розмір, не таймінг

Реального заліза/iverilog-симуляції для таймінгу не запускав (довго,
залежить від сусіднього репо fpga-lisp, не мета цього проходу). Розмір
згенерованого асемблера (11/126/437 інструкцій для трьох фікстур)
корелює з розміром джерела передбачувано лінійно й не показує сюрпризів
проти вже наявних evidence-записів (`evidence/length/` — 218 інструкцій
для реального `length`/`length-onto`).

## Практичний висновок для Cyberpunk-теми

Якщо мод-скрипт (dispatch-функція) викликається **один раз за сесію** —
AOT не варта своєї компіляційної ціни, простіше інтерпретувати.
Якщо викликається **регулярно протягом ігрової сесії** (dispatch на кожну
подію гравця) — AOT-компіляція один раз при завантаженні плагіна й
подальше пряме виконання дає реальну, велику (і, за застереженням вище,
консервативно оцінену) перевагу вже після кільканадцяти викликів.
